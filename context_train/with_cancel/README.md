# دليل شامل لاستخدام `context.WithCancel` في لغة Go

يوفر هذا المجلد أمثلة عملية وتطبيقية جاهزة للإنتاج توضح كيفية استخدام `context.WithCancel` في Go لإدارة دورة حياة الـ Goroutines وإلغائها بشكل آمن وسليم (Graceful Shutdown).

---

## 🎯 لماذا نستخدم `context.WithCancel`؟

في تطبيقات Go المتزامنة، نقوم كثيراً بإطلاق **Goroutines** لتنفيذ مهام في الخلفية. نحتاج إلى آلية موثوقة لإلغائها في الحالات التالية:

1. **إلغاء من قبل المستخدم (User Cancellation):** قيام العميل بإغلاق اتصال الـ HTTP أو النقر على زر إلغاء العملية.
2. **حدوث خطأ في مهمة فرعية حرجة:** فشل إحدى العمليات الأساسية مما يجعل استمرار باقي المهام غير مجدٍ.
3. **البحث التنافسي والأسرع وصولاً (Competitive Search / Race):** إرسال طلب إلى عدة سيرفرات أو مصادر بيانات في نفس الوقت، وأخذ أسرع نتيجة وإلغاء البقية لتوفير الموارد.
4. **منع تسرب الـ Goroutines (Goroutine Leaks):** ضمان إنهاء وتفريغ الـ Goroutines غير المستخدمة من الذاكرة بدلاً من بقائها معلقة في الخلفية إلى الأبد.

---

## ⚙️ كيف يعمل داخلياً؟

```go
ctx, cancel := context.WithCancel(parentContext)
defer cancel()
```

1. **`ctx.Done()`**: تُرجع قناة قراءة فقط (`<-chan struct{}`). تبقى هذه القناة مفتوحة حتى يتم استدعاء دالة `cancel()`. عند استدعائها، تُغلق القناة فوراً. يعمل إغلاق القناة كإشارة بث عام (Broadcast) تستلمها جميع الـ Goroutines المراقبة في نفس اللحظة.
2. **`cancel()`**: دالة استدعاء (Closure) مسؤولة عن إغلاق قناة `Done()`. وهي آمنة للاستخدام المتزامن (Thread-safe) ومتكررة الاستدعاء بأمان (Idempotent)؛ أي أن استدعاءها أكثر من مرة لا يسبب أي ضرر أو مشكلة.
3. **`ctx.Err()`**: تُرجع `nil` طالما أن الـ Context ما زال نشطاً. وبمجرد إلغائه، تُرجع الخطأ `context.Canceled`.

## 📂 السيناريوهات المشروحة في الكود ([`main.go`](main.go))

### 1️⃣ السيناريو الأول: الإيقاف السليم لمجموعة عمال (Worker Pool Graceful Shutdown)

- إنشاء 3 عمال (Goroutines) في الخلفية يعملون في حلقات مستمرة.
- كل عامل يراقب الإلغاء عبر:

  ```go
  select {
  case <-ctx.Done():
      // إنهاء العمل وتنظيف الموارد
      return
  default:
      // الاستمرار في العمل الطبيعي
  }
  ```

- المشرف يستدعي `cancel()` عند انتهاء الحاجة، مما يرسل إشارة لجميع العمال للتوقف بأمان.
- استخدام `sync.WaitGroup` للتأكد من خروج جميع العمال وإنهاء عملياتهم بالكامل قبل إغلاق البرنامج.

### 2️⃣ السيناريو الثاني: البحث التنافسي والإلغاء المبكر (Race & Early Exit)

- إرسال طلبات متوازية إلى 3 سيرفرات بسرعات استجابة مختلفة.
- بمجرد أن يستجيب السيرفر الأسرع بنتيجته، يتم استدعاء `cancel()` فوراً.
- تلتقط الـ Goroutines الخاصة بالسيرفرات المتبقية إشارة `<-ctx.Done()` وتلغي طلباتها فوراً، مما يوفر استهلاك المعالج وشبكة الاتصال.

### 3️⃣ السيناريو الثالث: الإلغاء الفوري عند حدوث خطأ (Fail-Fast on Error)

- تنفيذ 4 مهام فرعية بالتوازي لمعالجة طلب (فحص الحساب، الدفع، حجز المخزون، بوليصة الشحن).
- في حال حدوث خطأ في إحدى المهام (مثل: فشل الدفع بسبب عدم كفاية الرصيد)، يتم استدعاء `cancel()` فوراً.
- المهام الأخرى المتبقية التي لا تزال تعمل تستشعر `<-ctx.Done()` وتلغي أعمالها وتتراجع، مما يوفر الموارد ويمنع حدوث عمليات غير مكتملة أو معلقة.
- استخدام `sync.Once` لضمان التقاط أول خطأ وإلغاء السياق بشكل آمن ومنع سباق البيانات (Race Condition).

## 💡 أفضل الممارسات (Best Practices)

1. **استخدم دائماً `defer cancel()`**: استدعِ `defer cancel()` مباشرة بعد إنشاء الـ Context القابل للإلغاء لضمان تحرير الموارد في كل الأحوال وبغض النظر عن مسار خروج الدالة.
2. **مرر الـ Context كأول معامل دائماً**: اجعل المعامل الأول في الدوال هو `ctx context.Context`، مثل: `func doWork(ctx context.Context, id int)`.
3. **لا تقم بتخزين الـ Context داخل الـ Structs**: مرره صراحة عبر معاملات الدوال بدلاً من حفظه كحقل داخل بنية بيانات.
4. **التنسيق مع `sync.WaitGroup`**: عند تنسيق الإلغاء بين الـ Goroutines، استخدم `WaitGroup` لضمان إتمام مهام التنظيف قبل خروج التطبيق.
